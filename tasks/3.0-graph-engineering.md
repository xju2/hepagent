  Below is a practical implementation plan for turning **HepAgent** into a **graph-engineered agentic framework** for ATLAS physics analysis.

HepAgent already has the right skeleton to build on: it is a Python HEP agent framework with multi-provider LLM support, a CLI/REPL, tool extensibility, and an in-development JFC analysis pipeline that spans strategy, exploration, processing, inference, and documentation. The repository also already contains JFC-specific agent factories, a concurrent review gate with arbitration, orchestration/state persistence, commitment checking, and JFC tools under `src/hepagent/agents/jfc/` and `src/hepagent/tools/jfc/`.

## 1) Target idea: make the analysis a graph, not a script

The key design shift is to represent the physics analysis as an explicit **state graph**:

* **Nodes** are durable analysis objects: prompts, hypotheses, datasets, selections, plots, tables, notes, review reports, human decisions, and final artifacts.
* **Edges** encode dependencies and provenance: “derived-from”, “validated-by”, “rejected-by”, “supports”, “requires”, “commits-to”, “fixes”, “regresses-to”.
* **Agents** become graph operators: each agent reads a local subgraph, performs a bounded transformation, and writes new nodes/edges.
* **Review and human gates** are special nodes, not special cases in the overall architecture.

This fits HepAgent well because the current JFC implementation already uses discrete phase artifacts on disk, review gates, commitments, and saved orchestration state. The next step is to make those relationships first-class instead of implicit in the control flow.

## 2) Graph schema for ATLAS analysis

Start with a minimal, strongly typed graph schema.

### Node types

* `ProblemNode`: the physics question and analysis scope.
* `CommitmentNode`: Phase-1 commitments, each with an ID like `D1`.
* `DatasetNode`: data/MC samples, versions, luminosity, campaign.
* `MethodNode`: selection, reconstruction, calibration, statistical method.
* `ArtifactNode`: STRATEGY, EXPLORATION, SELECTION, INFERENCE, ANALYSIS_NOTE, figures.
* `EvidenceNode`: citations, numbers, closure tests, validation outputs.
* `ReviewNode`: reviewer findings and arbiter adjudication.
* `DecisionNode`: phase pass/iterate/escalate/regress decisions.
* `ExecutionNode`: tool calls, scripts, jobs, notebooks, batch submissions.

### Edge types

* `requires`: prerequisite relationship.
* `derives_from`: lineage/provenance.
* `supports`: evidence for a claim or decision.
* `invalidates`: reviewer or validation rejection.
* `commits_to`: phase commitment to downstream work.
* `resolves`: evidence that closes a commitment.
* `downscopes`: explicit narrowing of scope.
* `reviewed_by`: artifact to review node.
* `approved_by`: result of arbitration or human gate.
* `regresses_to`: later finding traced to an earlier phase.

This graph should be serializable to disk and reproducible from the analysis directory so that every claim in the final note can be traced back to a source artifact or computation.

## 3) What to preserve from the current HepAgent implementation

Do not throw away the current pipeline. It already provides the core operational pieces:

* The JFC executor agent assembles its prompt from an executor role document, phase templates, the physics prompt, upstream artifacts, and working-directory instructions.
* The review gate runs phase-specific reviewers concurrently and then runs an arbiter for phases that need adjudication.
* The orchestrator already saves state, resumes phases, handles commitment checks before Phase 4a, supports a human gate after Phase 4b, and commits phase progress to git.
* The JFC roadmap already separates skills, scaffolding, executor agents, review agents, orchestration, tools, commitment tracking, and CLI integration into distinct workstreams.

So the implementation plan is not “replace everything”; it is “recast the current phase pipeline as a graph runtime.”

## 4) Implementation architecture

### 4.1 Graph store

Implement a lightweight graph store first:

* Use JSONL or SQLite for the canonical store.
* Store each node with `id`, `type`, `content_ref`, `metadata`, `status`, `timestamps`.
* Store each edge with `src`, `dst`, `type`, `evidence_ref`, `created_by`, `phase`.

Keep the store local to the analysis root, alongside the current `.orchestration_state.json`, so runs remain self-contained and reproducible. The current orchestrator already persists run state to disk, which is a good pattern to extend.

### 4.2 Graph builder

Add a graph builder that:

* ingests `prompt.md`, phase outputs, logs, reviews, PDFs, and tables;
* extracts entities like datasets, selection cuts, observables, and commitments;
* creates nodes/edges incrementally after each phase and after each review gate.

The builder should not be an LLM-only step. Use deterministic parsing where possible, then let agents enrich the graph with semantic links.

### 4.3 Agent runtime over graph slices

Each agent should receive:

* a **subgraph view** relevant to the current task,
* a small set of required source artifacts,
* and an explicit “write-back contract” describing which node/edge types it may create.

This is the core graph-engineering principle: agents do not “know the world”; they operate on graph neighborhoods.

### 4.4 Review as graph validation

Convert reviews into graph operations:

* reviewer findings become `ReviewNode`s;
* each finding links to the exact artifact line, figure, or table it critiques;
* arbiter output becomes a `DecisionNode`;
* `PASS`/`ITERATE`/`ESCALATE`/`REGRESS` become edges that drive the orchestrator.

The current review gate already separates reviewer outputs from arbiter adjudication, so this maps cleanly.

### 4.5 Commitment management as graph constraints

The current commitment tracker is a good seed for graph constraints. Treat each `[D1]...[DN]` item as a `CommitmentNode`, and require:

* every commitment to have a downstream `resolves` or `downscopes` edge before Phase 4a proceeds,
* no silent deletion of commitments,
* every downscope to point to explicit evidence.

This aligns with the existing commitment-checking gate before Phase 4a.

## 5) Roadmap: six implementation milestones

### Milestone 1 — Define the graph contract

Deliver:

* schema for nodes/edges,
* serialization format,
* graph query helpers,
* validation rules.

Acceptance:

* can reconstruct the analysis graph from disk;
* can answer “what produced this plot?” and “what did this reviewer reject?” deterministically.

### Milestone 2 — Graph-aware scaffolding

Extend the existing scaffold tool so it creates not just folders, but also the initial graph:

* one `ProblemNode`,
* one `AnalysisRootNode`,
* placeholder `CommitmentNode`s,
* root provenance edges.

The JFC scaffold already exists as a dedicated tool in the roadmap and is meant to create the analysis directory structure and initial logbook.

### Milestone 3 — Phase executors that write graph updates

Wrap each phase executor so it must emit:

* the human-readable artifact,
* a machine-readable graph update file,
* and evidence pointers for major claims.

Phase 1 should produce commitments explicitly. Phase 2 should attach datasets and exploratory evidence. Phase 3 should attach method/selection decisions. Phase 4 should attach inference outputs and statistical evidence. Phase 5 should attach the final publication graph.

The current executor already gathers the physics prompt, upstream artifacts, and working directory context, which is exactly the right place to inject graph-writing instructions.

### Milestone 4 — Review/arbiter as graph consistency checks

Upgrade reviewers so they verify:

* every important claim has a provenance path;
* every plot corresponds to a declared figure node;
* every commitment is either resolved or downscoped;
* every number in the note matches the underlying machine-readable output.

Then make the arbiter produce a graph-level verdict:

* `PASS` only if the local subgraph is internally consistent,
* `ITERATE` if the graph is incomplete but repairable,
* `ESCALATE` if human attention is required,
* `REGRESS` if a later issue traces back to an earlier phase.

The current review gate already supports these kinds of verdicts and concurrency.

### Milestone 5 — Graph-driven orchestration and resumption

Refactor the orchestrator so it no longer thinks only in linear phases. It should:

* traverse the graph frontier,
* identify unresolved dependencies,
* decide which subgraph to expand next,
* and resume from the most recent consistent checkpoint.

The current orchestrator already persists state, supports resumption, and can rewind after regression findings, which is the right foundation for this step.

### Milestone 6 — Final note generation from the graph

Make the analysis note writer consume the graph directly:

* every section in the note should map to a graph neighborhood,
* every figure reference should resolve to a figure node,
* every claim should point to evidence edges,
* every summary table should be backed by machine-readable data.

That will make the final PDF reproducible and reviewable from the graph rather than from ad hoc prompt history. The current note-writer and typesetter flow already exists and can be upgraded in place.

## 6) ATLAS-specific design choices

For ATLAS, the graph should capture experiment-specific structure:

* dataset/campaign/AMI tags,
* detector and reconstruction version,
* trigger menu and luminosity blocks,
* systematic sources and nuisance parameters,
* analysis regions and control regions,
* statistical model components,
* approval/review checkpoints.

That means the graph is not only an agent memory; it becomes the canonical analysis ledger.

## 7) What success looks like

A successful graph-engineered HepAgent should be able to:

* start from a short physics question,
* generate a reproducible analysis graph,
* run analysis phases with explicit provenance,
* surface missing evidence before it becomes a silent error,
* and produce a final note whose every claim can be traced back through the graph.

The current JFC pipeline already points in this direction: it is phased, reviewed, stateful, resumable, and commitment-aware. The implementation plan above makes that structure explicit and extensible.
