# 4.0 — Authored analysis graphs

`tasks/3.0-graph-engineering.md` made the analysis graph the ledger of a JFC run
and let the planner *derive* execution order from it. What it did not do is let
anyone **author** that structure. The shape of an analysis is still hardcoded
across roughly fifteen parallel tables:

- `PHASE_SPECS` + `UPSTREAM_ARTIFACTS` (`agents/jfc/executor.py`) — the de-facto DAG
- `PHASE_ORDER` (`agents/jfc/planner.py`), mirrored again in `graph_builder.py`
- `AN_PHASES`, `_AN_OUTPUT_MAP`, `_AN_PDF_MAP` (`orchestrator.py`)
- `_PHASE_REVIEWERS`, `_ARBITER_PHASES`, `phase_dir_map` (`review_gate.py`)
- `PHASE_CONTRACTS` (`tools/jfc/graph.py`)
- `PHASE_DIRS`, `_PHASE_TEMPLATE_MAP` (`tools/jfc/scaffold.py`)
- phase→directory maps duplicated again in `reviewers.py`, `fixer.py`,
  `tools/jfc/artifacts.py`, `tools/jfc/figures.py` and `main.py`

plus three gates written as `if phase == "4a"` / `if phase == 1 and codesign` /
`if phase == "4b"` inside `run_jfc_analysis`.

A real analysis is not always that shape. `data/methodology/09-multichannel.md`
already describes multi-channel fan-out — per-channel exploration and selection
that merge at inference — and shared calibration sub-analyses. The runtime cannot
express either.

## Goal

Make the analysis structure a first-class, user-authored document. An Architect
agent proposes it from the physics prompt; the user reviews and edits it in a
browser — nodes, prompts, edges, edge attributes — **before any agent work
begins**; a generalised runtime executes it. The seven-phase JFC layout becomes
the built-in default template, not the only shape.

## Design decisions

1. **A separate, mutable document.** `<analysis_root>/plan.json` plus
   `plan.history/`, which *compiles into* the append-only provenance graph. Every
   `docs/GRAPH.md` invariant stays intact — the graph remains append-only,
   idempotent, and never raises into the orchestrator. Append-only semantics would
   fight editing: deleting a node would need a tombstone and every reader would
   have to replay the log to know the current shape.
2. **A dedicated editor page**, not a Chainlit custom element. Chainlit's JSX
   sandbox whitelist is react + shadcn/ui + lucide only — no graph library — so an
   element-hosted editor would be hand-rolled SVG that CI cannot test. Instead our
   own FastAPI routes are mounted on the same uvicorn app: `GET /plan/{name}`
   serves one self-contained HTML/SVG editor, `/api/plan/{name}` is JSON.
   *Verified against chainlit 2.11.1*: its SPA catch-all is registered at import
   time, so our routes must be **inserted at the front** of `app.router.routes`;
   with that, `/plan/{name}`, `/api/plan/{name}` and Chainlit's own `/` all serve.
3. **Phase-shaped nodes.** A node stays "a working directory + a primary artifact
   + an executor prompt + a reviewer set". A `kind` discriminator and a `tools`
   allowlist are in the schema so fully general agent nodes stay additive.
4. **Clean redesign, no bug-for-bug compatibility.** Phase keys become
   author-stable slugs; the `int | str` phase key and its reconciliation helpers
   go away. Existing analyses get `hepagent jfc plan migrate`.
   *Exception*: the default template keeps the current on-disk directory and
   artifact names, because the `data/methodology/` and `data/conventions/` corpus
   cites those paths by name.

## Progress report

**Status:** M1–M5 implemented. Task complete.

### M1 — the plan layer

New `src/hepagent/plan/` package, domain-agnostic except for one module:

- **`schema.py`** — `AnalysisPlan`, `PlanNode`, `PlanEdge`, `PlanGate`,
  `PlanContract` as frozen dataclasses, with the same unknown-key-dropping
  `from_dict` as `graph/schema.py` so a plan written by a newer build still loads.
- **`store.py`** — whole-document read/write of `plan.json`. Every save archives
  the version it replaces to `plan.history/<revision>.json` and bumps `revision`.
  The revision on an incoming plan is ignored: it is a property of the file, not
  of the caller.
- **`validate.py`** — rules P1–P9, **reusing `graph.validation.GraphFinding` and
  `GraphValidationReport`** rather than a parallel type, so the error/warning
  severity model and the `blocking`/`advisory` split are literally the same code.
- **`compile.py`** — `plan_to_graph` (pure, touches no disk) and
  `execution_order`.
- **`layout.py`** — deterministic layered layout, computed in Python so the
  browser only draws and the geometry is unit-testable.
- **`templates/`** — `jfc-measurement.json`, `jfc-search.json` and a registry.
  Template nodes carry a `prompt_ref` into the JFC data directory; `instantiate`
  inlines the markdown and substitutes the `{{name}}`-style placeholders, so the
  `plan.json` that lands in an analysis always holds literal, editable prompt text.
- **`service.py`** — the stdlib-only façade the CLI and the web router will share,
  plus `PlanApprovalGate`: one `asyncio.Event` per analysis root, which is the
  handshake that makes "review before any agentic work begins" real.

Two design points settled while building, both departures from the written plan:

- **`PlanEdge` names its endpoints `upstream`/`downstream`, never `src`/`dst`.**
  A plan edge reads in data-flow order; a graph `requires` edge reads in
  dependency order and puts the *dependent* node in `src`. Naming them
  differently makes the inversion impossible to write by accident, and
  `compile.plan_to_graph` is the single place it happens.
- **Ambient files moved from the edge to the node** (`PlanNode.context_paths`).
  `COMMITMENTS.md` was in `UPSTREAM_ARTIFACTS` but was never a phase prerequisite
  — `bootstrap_graph` filtered it out with an implicit `"/outputs/"` string test.
  It belongs to the node that reads it, not to one of its dependencies, and the
  filter is now explicit: only `requires` edges order execution.

**Gates carry position.** The three gates JFC grew are not all of one kind — the
commitment check blocks a node from starting, while the codesign and human
reviews judge what it produced — so `PlanGate` declares `when` ∈
`before`/`after` rather than implying it from the gate's name. The codesign gate
ships `enabled: false`, so `--codesign` will flip data instead of branching on a
node id.

### M2 — the runtime reads the plan

Every table that encoded the pipeline is gone. What replaced each one:

| Deleted | Now read from |
|---|---|
| `PHASE_SPECS`, `UPSTREAM_ARTIFACTS` (executor) | `node.directory` / `node.artifact` / `node.prompt`; `plan.upstream_edges(node.id)` |
| `PHASE_ORDER` (planner, orchestrator, graph_builder) | `requires` edges compiled from the plan; plan declaration order breaks ties |
| `AN_PHASES`, `_AN_OUTPUT_MAP`, `_AN_PDF_MAP` | `node.produces_note`, `node.note_path`, `node.note_pdf_path` |
| `_PHASE_REVIEWERS`, `_ARBITER_PHASES`, `phase_dir_map` | `node.reviewers`, `node.arbiter`, `node.directory` |
| `PHASE_CONTRACTS` (tools/jfc/graph.py) | `node.contract` |
| `PHASE_DIRS`, `_PHASE_TEMPLATE_MAP` (scaffold) | `plan.nodes` — the scaffold no longer knows how many there are |
| `_ARTIFACT_MAP`, `_PHASE_DIR_MAP` (artifacts, figures) | `tools/jfc/_resolve.resolve_node`, reading `plan.json` |
| `if phase == "4a"` / `"4b"` / codesign branch | `node.gates` dispatched by `_run_gates(node, when)` |
| `PHASE_ORDER[origin:detected+1]` | `_between(plan, origin, detected)` = descendants(origin) ∩ ancestors(detected) |
| `phase_names` + hardcoded `/7` (CLI) | `plan.nodes` |

**Phase keys became node ids everywhere.** `JFCOrchestrationState` now carries
`current_node` / `completed_nodes`; `model_validate_json` drops keys it no longer
knows, so an older state file still loads. The five `int | str` reconciliation
helpers (`_canonical_phase`, `_coerce_phase`, `_parse_origin_phase`, `phase_key`,
`_rank`) are gone — a node id is a string, always.

Three departures from the written plan, each because building it exposed
something the plan assumed:

- **R3's Phase-1 exemption became a graph question, not a plan lookup.** The rule
  "the entry artifact legitimately has no lineage" is answerable from the graph
  alone — an artifact with no `requires` edge to another artifact is an entry —
  so `graph/validation.py` needs no plan, and a branching plan with several entry
  nodes gets the right answer for free.
- **R6's note glob does read the plan**, because a note artifact is not otherwise
  distinguishable from any other markdown in an outputs directory. `_analysis_notes`
  now returns the `note_path` of every `produces_note` node, falling back to the
  old `*/outputs/ANALYSIS_NOTE_*.md` glob when no plan is readable so a
  half-scaffolded directory still validates. A stray `SCRATCH_NOTES.md` is no
  longer checked as if it were a note — there is a test for exactly that.
- **`resolve_node` is shared, in `tools/jfc/_resolve.py`.** Three tool modules
  needed the same "node id → PlanNode, or an agent-readable error" lookup. It
  returns a message rather than raising: a tool that raises loses the turn,
  whereas one that names the valid node ids gets corrected.

**Migration.** `hepagent jfc plan migrate --name X` instantiates the template,
remaps `completed_phases` → `completed_nodes` through `PHASE_TO_NODE`, and
rewrites the state file. Phase keys with no counterpart are *dropped and
reported*, not guessed at — carrying one forward would make `completed_nodes`
lie. Because the shipped template keeps the legacy directory and artifact names,
and graph node ids are content-addressed on paths, the provenance graph survives
untouched; only `Node.phase` changes, which `graph rebuild` refreshes.

**New CLI:** `jfc templates`, `jfc plan show|validate|migrate`, `--template` and
`--plan` on `jfc run`. `jfc status` and `jfc list` read node counts from the plan;
`jfc resume` takes a node id. `plan show --format` renders table, mermaid or JSON
from the new `plan/report.py`, which M4's `/plan` slash command will reuse.

### M3 — the architect

**The architect proposes edits, not a plan.** This is the one design decision in
M3 that everything else follows from, and it is a departure from the written
plan's "returns a plan as structured output".

The shipped node prompts run to thousands of words each and are the product of
the `methodology/` corpus. A model asked to return a whole plan must reproduce
them, and what it actually does is paraphrase them — and the paraphrase is what
would then run. Asking for a short edit list instead means the prompts survive
byte-identical unless the architect deliberately rewrites one, and it means the
proposal is reviewable: six edits are something a physicist reads, a regenerated
seven-node plan is not.

Six operations, in `plan/edits.py` — pure, model-free, and tested on its own:

| op | Effect |
|---|---|
| `split_node` | Replace a node with copies sharing its wiring, reviewers, contract and gates. **The multi-channel primitive.** |
| `add_node` | Add a node; `like` inherits reviewers/contract/gates from an existing one |
| `remove_node` | Remove a node and every edge touching it |
| `add_edge` / `remove_edge` | Rewire, with `kind` and `inject` |
| `set_prompt` | Replace a node's prompt wholesale |

Three properties make this safe to hand to a model:

- **An edit that cannot be applied is skipped and reported**, never fatal. A
  proposal that is half-right produces a half-edited plan plus a note per
  rejection, rather than nothing.
- **`split_node` derives directories from the new ids** rather than taking them
  from the proposal, so replicas cannot collide on disk — the P2 uniqueness rule
  cannot be violated by a careless split.
- **A copied node never inherits `produces_note`.** Two nodes writing the same
  analysis note would fight over the file.

**The proposal is never trusted.** `propose_plan` applies the edits, runs
`validate_plan`, and on blocking findings feeds them back *by rule and message*
for exactly one repair round. A proposal that still does not validate is
discarded and the plain template runs. So does a model error, an unstructured
answer, or a failed repair. The worst case is the behaviour we had before the
architect existed, which is what makes it safe to run by default — and there is
a test asserting the returned plan validates for every failure mode.

`ArchitectProposal` is a flat pydantic model with unused fields left null rather
than a discriminated union: models emit it far more reliably, and two tests pin
that it survives the SDK's strict JSON schema generation and round-trips a
realistic payload — the stubs in the rest of the suite bypass that layer, and a
type that cannot be expressed strictly would otherwise fail only against a real
provider.

**`data/agents/README.md` was rewritten**, not just appended to. It ships in the
wheel as the auditable role catalogue and its phase-activation tables still
described the fixed pipeline. It now says plainly that node/reviewer assignment
is authored in `plan.json` and that its tables describe the shipped default;
`test_plan_templates.py` asserts every reviewer the template uses appears in it.

**New CLI:** `jfc plan propose --name X --prompt-file p.md [--type] [--template]
[--model] [--out]`. It saves into the analysis directory when one exists
(versioned through `plan.history/`), otherwise writes `<name>-plan.json` and
prints the `jfc run --plan ...` command to run it.

### M4 — the plan editor

The layer that makes the whole task's premise real: a physicist sees the analysis
graph, edits it, and *then* agents start.

**Route ordering was the hazard the design predicted, and it is now pinned from
both sides.** Chainlit registers `/{full_path:path}` at import time and Starlette
matches in order, so `include_router` puts our routes where a GET never reaches
them — `/api/plan/zbb` would silently return the SPA shell instead of JSON.
`plan_api.mount` splices them in at `app.router.routes[:0]`. Two tests sit next
to each other: one asserts the mount works behind a catch-all, and its neighbour
asserts that `include_router` *would not have*, so a refactor back to the obvious
call fails loudly rather than producing a mysteriously blank editor.

**Import boundaries.** `docs/WEB.md` invariant 1 was "only `app.py` imports
Chainlit"; it is now "…and only `plan_api.py` imports FastAPI". `session.py` and
`server.py` are on paths that run without either extra, so they import `fastapi`,
`uvicorn` and `chainlit` inside functions only. This is enforced by an AST test
rather than a convention — `test_only_plan_api_imports_fastapi` walks
`web/*.py` module scope and fails on any of the three.

This bit twice while building. The first version of the `/plan` chat command
imported `analyses_dir` from `plan_api`, which drags FastAPI into a CI path that
has none. The fix was to move `analyses_dir`, `resolve_analysis` and
`list_planned` down into `plan/service.py`, which is where they belonged anyway:
they are plan-location questions, not HTTP ones.

**Path safety.** `PUT /api/plan/{name}` writes files and the name comes from a
URL, so `service.resolve_analysis` refuses anything resolving outside the base
directory; the route only turns that into a 400. Tested against `../secret`,
`..%2Fsecret` and `a/../../etc`, including a test that asserts nothing was
written outside.

**The page.** One self-contained file — inline CSS and JS, SVG rendering, zero
external requests, light and dark. Server-computed layout from `plan/layout.py`;
drag persists to `node.metadata.x/y` and "Auto-layout" clears it again. Clicking
a node opens a panel for label, directory, artifact, prompt, reviewers, arbiter,
gates and their `before`/`after` position, the write-back contract, model
override and iteration budget; clicking an edge edits `kind` and `inject` with a
sentence explaining what each choice does. A findings bar sits under the canvas,
errors first, each row clicking through to the offending node. **Approve & run**
is disabled while anything blocks *or* while there are unsaved changes.

**The page's JavaScript is tested, not assumed.** `tests/web/test_plan_editor_js.py`
extracts the inline script and runs it in Node against a stub DOM
(`plan_editor_harness.mjs`), which implements exactly what the page touches — so
a page change needing more of the DOM fails loudly here instead of silently in a
browser. Thirteen assertions cover: every node and edge is drawn (`svg_children`
equals `defs + 2·edges + nodes` exactly), positions come from the layout until a
drag and from `metadata` after, a new node arrives with a reviewer and a prompt
rather than as a trap, editing disables approval, connect-mode makes exactly one
`requires`/`full` edge and refuses a self-edge, saving sends the whole document,
and approving unsaved work saves first. That last one caught a *harness* bug, not
a page bug: mutating a node directly does not set the dirty flag, because the
real edit path goes through the input handler that calls `markDirty()`.

**The approval handshake is tested across both subsystems.**
`tests/web/test_plan_approval_flow.py` starts a real `run_jfc_analysis(
require_approval=True)`, confirms it parks at the latch, and releases it with a
real `POST /api/plan/{name}/approve` — no model calls, agents stubbed. It also
pins three things neither side's own tests would catch: a plan edited while the
run waits is the plan that runs (the deleted node never executes), saving
*withdraws* approval so an edit cannot accidentally start the run, and a plan
with a cycle returns 409 and leaves the run parked.

**New entry points:** `hepagent jfc plan edit --name X [--until-approved]`
(bare uvicorn, no Chainlit — much the heavier half of the extra),
`hepagent jfc run ... --review-plan` (editor and run in one process and one loop,
which is the only way the browser's button and the orchestrator's `await` can be
the same latch), `hepagent web --base-dir`, and `/plan [name]` in the chat, which
lists analyses or renders one as Mermaid with a link to its editor.

### The CI failure

The PR's first CI run failed with seven `ModuleNotFoundError: No module named
'fastapi'` errors. `plan_api.py` re-exported `service.BASE_DIR_ENV` and
`service.analyses_dir`, and `session.py`/`server.py` imported them from there —
so a module that must run without the `web` extra reached FastAPI through a
module that looked like a safe import. It passed locally because the dev
environment has the extra.

Fixed by pointing both callers at `plan.service` and deleting the re-exports, so
the tempting import no longer exists.

The guard was the real problem. `test_only_plan_api_imports_fastapi` parses
module-scope imports and explicitly allows function-local ones — it cannot
distinguish a safe `import fastapi` inside a web-extra entry point from an unsafe
import of a FastAPI-importing module. Replaced the reliance on it with a
`without_web_extras` fixture in `tests/conftest.py` that blocks the extras via a
`sys.meta_path` finder (and evicts a cached `plan_api`, so the result does not
depend on test order) and *runs* the code. Both new tests were confirmed to fail
against the bad imports before the fix went in, and
`test_the_extras_blocker_actually_blocks` keeps them from passing vacuously.

All three reproduced against the real code before anything was changed, and the

### 1. An open commitment made the first node unpassable (P1)

`write_graph_validation` ran *every* rule, including R2 ("commitment has no
closing edge"), at every node review. The strategy node declares the analysis's
commitments, so its own review re-reported the rows it had just written, as
errors, which the gate turns into PASS → ITERATE. Nothing able to close them runs
until much later, so the node burned its iteration limit and stopped.

Split R2: `rule_commitments_closed` (timing-dependent, due at the `commitments`
gate) and `rule_downscopes_justified` / R2b (timing-independent — a downscope
with no evidence is wrong when written). Added `REVIEW_RULES`, which is
`ALL_RULES` minus R2, and pointed `write_graph_validation` at it.

This selects which rules apply at which checkpoint rather than overriding a
severity, so invariant 7 survives. New invariant 9 records the trap.

### 2. An authored plan could scaffold outside the analysis root (P1)

`--plan` reached `scaffold_jfc_analysis` without ever being validated, and
`_write_node_tree` joined `node.directory` onto the root unchecked. A plan with
`directory: "../other-project"` created directories and overwrote `CLAUDE.md`
outside the analysis. P2 detects exactly this — nothing was asking it.

`orchestrator.require_runnable_plan` now raises `PlanNotRunnableError` on any
blocking finding, called before the scaffolder and again in `_prepare_plan` (so a
hand-edited `plan.json` on disk is checked too). `scaffold._node_dir` re-checks
containment where the write actually happens, so a caller that skips validation
still cannot escape.

### 3. A passed node stayed rejected forever (P2)

Both review rounds write the same `ADJUDICATION.md` and so share one
content-addressed decision id. A later PASS supersedes the decision node but
cannot remove the `invalidates` edge the ITERATE round wrote — the log is
append-only and the two edges have different keys. `query.rejections` kept
returning it, so `is_consistent_checkpoint` was false for an artifact that had
passed and resume rewound past completed work.

`query.rejections` now skips decisions whose current verdict is PASS: the
decision node is the single record of that adjudication, so its verdict is the
authority. New invariant 10 records it.
